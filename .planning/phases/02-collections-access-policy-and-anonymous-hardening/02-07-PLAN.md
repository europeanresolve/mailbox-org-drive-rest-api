Source: ROADMAP Phase 2 Goal and success criteria 1-5, restated in user-story form. This plan delivers the Idempotency-Key clause of success criterion 2: a retry with the same key returns the original result and creates no duplicate.

Entry shape in the MongoDB collection `_idempotency` (the leading underscore keeps it apart from `records_<name>`):
`{ _id: sha256hex(collection + "\n" + key), principal: "<api key name>" | "anonymous", bodyHash, status: "pending" | "complete", recordId, createdAt: Date, lockedAt: Date, response?: { status, etag, body } }`.
`createdAt` must be a BSON Date for the TTL index. The raw Idempotency-Key is never stored or logged.

Create flow with a key, after the honeypot check and validation (plan 02-06 order):
1. `begin()` inserts a pending entry with a fresh recordId. If the insert succeeds, store the record with that id, `complete()` the entry with the response, reply.
2. On a duplicate-key error, read the entry: a different principal or bodyHash gives 422; complete gives a replay of the stored response; pending with a lock younger than 30 s gives 409; an older lock is taken over with one atomic findOneAndUpdate on `{ _id, status: "pending", lockedAt: <the value read> }`. The winner stores the record with the entry's recordId (a duplicate-key error on the record means it was already stored, so read it back and build the response), then completes the entry; the loser gets 409.
3. If storing the record fails for any other reason, `abandon()` deletes the pending entry so a retry can proceed, then the error reaches the normal 500 handler.
This is the pessimistic pending pattern from research Pitfall 4, plus the pre-chosen record id so a takeover cannot duplicate.

Why the principal is stored: D-09 scopes keys per collection and key value. Storing who created the entry keeps that scoping, and refusing a different principal with 422 stops one API key from reading another key's original response.
