## Phase Goal

**As a** deployer running a website for a small organisation, **I want to** define collections in config, let the website submit forms to hardened anonymous create endpoints, and manage the records through API-key-protected CRUD with default-deny access, **so that** form submissions land safely in the system of record without me running a CMS.

Source: ROADMAP Phase 2 Goal and success criteria 1-5, restated in user-story form. This plan delivers the list part of success criterion 3: list records with cursor pagination and equality/range filters on indexed fields only, where a filter on a non-indexed field is rejected.

<objective>
User story slice: a backend with a key can list a collection's records page by page and filter them by the fields the deployer chose to index.

Purpose: COLL-03 with decisions D-17, D-18, D-19.
Output: `indexes` collection config key and its startup checks, the list query parser and cursor codec, RecordStore.list, GET /v1/{name}, index creation, tests.
</objective>

Builds on plan 02-01: records live in `records_<name>` as `{ _id, _v, createdAt, updatedAt, data }`, so an indexed path `address.country` is the MongoDB field `data.address.country`. Response items use the flattened record shape from 02-01.

List envelope (CONTEXT.md discretion): `{ items: [...records], nextCursor: string | null }`. No ETag on list responses.

Cursor: base64url of JSON `{ s, v, id }` where `s` is the sort spec string (for example `-createdAt`), `v` the last item's sort value and `id` its _id. A cursor whose `s` differs from the request's sort, whose `v` is not a scalar of the sort field's type, or whose `id` is not a string is a 400. This check is what stops a crafted cursor from smuggling a MongoDB operator object into the filter.
