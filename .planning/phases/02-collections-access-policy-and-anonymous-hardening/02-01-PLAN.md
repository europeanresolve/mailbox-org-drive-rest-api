## Phase Goal

**As a** deployer running a website for a small organisation, **I want to** define collections in config, let the website submit forms to hardened anonymous create endpoints, and manage the records through API-key-protected CRUD with default-deny access, **so that** form submissions land safely in the system of record without me running a CMS.

Source: ROADMAP Phase 2 Goal and success criteria 1-5, restated in user-story form (the ROADMAP Goal line is not written as a story). Success criterion 2's CAPTCHA clause is void per D-07.

This plan is the tracer for the phase. One collection in config, an anonymous `POST /v1/{name}` and an apiKey `GET /v1/{name}/{id}` run through the real composition root (`start()`), with strict validation, against MongoDB on the Compose stack. Every later plan expands from this slice.

Design choices for this phase, made under CONTEXT.md "Claude's Discretion" and used by every later plan:
- Config layout: `collections.<name>` holds `schema` (an inline JSON Schema object, or `{ $ref: "<relative path>" }` naming a JSON or YAML file inside the config file's directory, per Phase 1 D-18) and `operations` (a map from `create|get|list|replace|patch|delete` to `anonymous|apiKey`). Later plans add `indexes`, `honeypot`, `cors`, `rateLimit`, `bodyLimit` to the same object and `trustProxy`, `docs` to `server`. Top-level `apiKeys` is a list of `{ name, hash, grants }`.
- Key format: `mdra_` followed by 43 base64url characters (32 random bytes). The configured hash is lowercase SHA-256 hex of the whole key string, prefix included. There is no key id inside the key; the store hashes the presented key and compares it with every configured hash.
- An operation with no policy is never registered, so it answers the normal 404 problem+json. This hides which collections exist from anonymous callers and keeps denied operations out of /docs.
- MongoDB layout: one MongoDB collection `records_<name>` per configured collection, documents `{ _id: <uuid>, _v: <int>, createdAt: <ISO string>, updatedAt: <ISO string>, data: { ...user fields } }`. User fields live under `data` so they can never collide with server fields. The database is the one named in the Mongo URI (`client.db()`).
- Response record shape: `{ id, createdAt, updatedAt, ...data }`. Anonymous create returns only `{ id, createdAt }` (COLL-08). Every create, GET, PUT and PATCH sends `ETag: "<_v>"` (D-20), so create always sends `"1"`.
- Record bodies are validated in the route handler with the precompiled strict validator, not through Fastify's route `schema.body`. Fastify's own Ajv coerces and strips (research Pitfall 1), and the handler order also lets plan 02-05 remove the honeypot before validation.
- 400 problem bodies may carry `errors: [{ keyword, pointer? }]`. `pointer` is the Ajv instancePath only when every segment is an array index or a property name declared in the schema, so a submitted property name or value is never echoed.
