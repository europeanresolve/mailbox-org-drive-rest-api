## Phase Goal

**As a** deployer running a website for a small organisation, **I want to** define collections in config, let the website submit forms to hardened anonymous create endpoints, and manage the records through API-key-protected CRUD with default-deny access, **so that** form submissions land safely in the system of record without me running a CMS.

Source: ROADMAP Phase 2 Goal and success criteria 1-5, restated in user-story form. This plan delivers two clauses of success criterion 5: a browser request from an origin not allowed for the collection is rejected, and the per-IP rate limit still holds when a client forges `X-Forwarded-For`.

<objective>
User story slice: a website's own pages can post to the API from the browser, other sites cannot, and one client cannot flood the anonymous endpoints, even by forging proxy headers.

Purpose: SEC-04 and SEC-05, implementing D-10, D-11, D-12. Resolves research assumption A2 (rate-limit and trustProxy) by putting trustProxy on the Fastify instance, so `request.ip`, which @fastify/rate-limit keys on by default, already honours it.
Output: config keys, startup checks, CORS and rate-limit wiring, tests.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser on another site -> collection routes | cross-origin requests carrying the user's network position |
| untrusted peer -> X-Forwarded-For | client-controlled header claiming another IP |
| trusted proxy (Kong) -> API | forwarded client IP believed only from listed addresses |
