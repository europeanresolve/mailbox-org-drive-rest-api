## Phase Goal

**As a** developer building on this service, **I want to** start the local stack with one command, run the full test suite green in CI, and rely on a configurable, path-safe, retry-aware storage layer, **so that** I can build the website-forms features on documented mailbox.org WebDAV behaviour without touching a real Drive or leaking secrets and personal data into logs.

Source: ROADMAP Phase 1 Goal and success criteria 1-5.

This plan delivers the "retry-aware" part and completes ROADMAP success criterion 5. The WebDAV adapter passes the same contract suite that the in-memory adapter passes, retries only transient failures, caps concurrency and never sends deep PROPFINDs.

<objective>
User story: as a developer building on this service, I want a one-command local stack, a green CI suite and a safe storage layer, so that I can build the forms features on documented mailbox.org behaviour without leaking data.

This plan's slice: implement `WebDavAdapter` on the `webdav` client with a concurrency cap, bounded retry, a 401 cooldown, path-free error mapping and the semantic rules the contract requires. Prove it with a fault-injecting in-process server and the shared contract against Compose.

Purpose: STOR-04 and STOR-05. mailbox.org publishes no rate limits (D-09), so the adapter must be gentle and must never leak a person's folder name through library errors (research Pitfall 1).
Output: `src/storage/webdav-adapter.ts`, the fake server helper, unit and integration tests.
</objective>
