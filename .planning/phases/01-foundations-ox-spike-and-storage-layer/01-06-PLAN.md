## Phase Goal

**As a** developer building on this service, **I want to** start the local stack with one command, run the full test suite green in CI, and rely on a configurable, path-safe, retry-aware storage layer, **so that** I can build the website-forms features on documented mailbox.org WebDAV behaviour without touching a real Drive or leaking secrets and personal data into logs.

Source: ROADMAP Phase 1 Goal and success criteria 1-5.

This plan delivers ROADMAP success criterion 2's first clause. A deployer who starts the service with an invalid config (file plus environment, secrets also via `*_FILE`) gets one startup failure listing every config error.

<assumption_delta_decision>
Detector signal: pluralization ("secrets also via `*_FILE`"). The primary noun is the placeholder name `${NAME}`: one identity with exactly one value source, either env `NAME` or the file at `NAME_FILE`. Decision: promote. The placeholder is the identity and the source is a detail, so both-set is an error rather than one source silently overriding the other. Invariant test (accepted, Task 2): the same config resolves to a deep-equal Config whether a secret comes from `NAME` or from `NAME_FILE`.
</assumption_delta_decision>

<objective>
User story: as a developer building on this service, I want a one-command local stack, a green CI suite and a safe storage layer, so that I can build the forms features on documented mailbox.org behaviour without leaking data.

This plan's slice: build the fail-fast YAML config loader and wire it into the composition root.

Purpose: FND-01. The config file is the deployer contract (D-16..D-18), and its errors must never echo secrets (research Pitfall 2).
Output: `src/config/{schema,load}.ts`, config-aware `start()`, `config/config.example.yaml`, fixtures and tests.
</objective>
