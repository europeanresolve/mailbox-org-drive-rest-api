Choices made here under CONTEXT.md "Claude's Discretion" (rebuild semantics, status payload):
- GET /mirror/status → 200 `{ collections: [...] }` in config order, `Cache-Control: no-store`. `lagSeconds` = whole seconds since pendingSince, 0 when nothing is pending; `pendingWrites` = max(0, dirtySeq − mirroredSeq); timestamps as ISO strings or null.
- POST /mirror → 202 `{ status: "accepted", collections: [<names>] }`; optional query `collection`. `requestRebuild(names)` upserts `$set: { forceUpload: true, reconcileRequested: true }` and unsets nextAttemptAt, so the worker picks it up on its next tick and an operator repair is not delayed by backoff.
- Worker: when forceUpload is set the D-04 skip is bypassed; the fenced commit sets forceUpload to false.
- Registration: one ConfigKeyStore built in server.ts is shared by the collection routes (existing `keyStore` option of registerCollections) and the mirror routes. Mirror routes are registered for every role when config.mirror exists (Task 1 confirms this), so a worker-only deployment stays operable.
- `/ready` is unchanged: mirror health is informational and lives in /mirror/status (ARCHITECTURE; Drive outages never fail readiness).
</context>
