# Project brief: mailbox-org-drive-rest-api

> Input for `/gsd:new-project --auto @PROJECT-BRIEF.md`. It records the decisions from the exploratory discussion, so GSD can generate `.planning/` (PROJECT, REQUIREMENTS, ROADMAP, STATE) from it.

## One-liner

A generic, self-hostable REST API that stores JSON records (mirrored to `.xlsx`), serves `.xlsx` sheets as JSON and `.docx` documents as Markdown, all backed by a mailbox.org Drive over WebDAV.

## Problem

Small organisations (first user: a European civil-society non-profit) already store everything in mailbox.org Drive. Their website needs to:

1. accept form submissions that staff can read as spreadsheets;
2. publish content that staff edit in Drive (a spreadsheet of articles plus a `.docx` for each article);
3. later, serve research publications and larger files.

Running a CMS or a separate storage service is more than they can maintain. mailbox.org offers WebDAV access to Drive but no REST API, and we found no existing open-source REST layer for it.

## Users

- **Deployers / developers**: configure collections, mounts and access, and run the service.
- **API consumers**: a website backend or frontend, and internal tools.
- **Staff (indirectly)**: open mirrored `.xlsx` files and edit content files in Drive. They never call the API themselves.

## Core value

Staff keep working in the Drive they already use, and developers get a safe, fast JSON API on top of it.

## Locked decisions

| Topic | Decision |
|-------|----------|
| Scope | **Generic and organisation-agnostic.** No organisation names, folder layouts or schemas in this repo. Organisation-specific use (e.g. a newsfeed) lives in the consuming website's own backend directory. |
| Repository | Public. Name: `mailbox-org-drive-rest-api`. |
| Licence | EUPL-1.2. |
| Language | TypeScript on Node.js LTS. |
| HTTP framework | Fastify (default choice; it has native JSON Schema validation and OpenAPI support). Can be revisited in phase 1. |
| Write storage | **MongoDB is the system of record** for collection records. The Drive `.xlsx` is a one-way mirror, regenerated by a single background writer. People treat it as read-only. |
| Read storage | Drive is the source of truth for sheets, documents and files. MongoDB caches parsed sheets and converted documents, keyed on the WebDAV ETag / last-modified date. |
| Storage access | A WebDAV adapter behind a `StorageAdapter` interface, so an S3 backend can be added later. |
| Drive access scoping | Allow-listed **mounts** (named folder plus `read` / `read-write` mode). The documentation recommends a dedicated service account. |
| `.docx` → Markdown | mammoth (`.docx` → HTML), then turndown (HTML → Markdown). mammoth's own Markdown output is deprecated. |
| `.xlsx` | exceljs. |
| Auth, v1 | Per-collection, per-operation policy: `anonymous` or `apiKey`. |
| Auth, later | `oidc`: validate JWTs from Keycloak (or any OIDC provider), with role claims mapped to policies. Keycloak is **not** deployed until internal forms need it. |
| Rate limiting | At the gateway: a Kong reference config in `deploy/`. Light in-app limits (`@fastify/rate-limit`) as a fallback for deployments without a gateway. |
| Object storage | Deferred. An S3-compatible API for research materials is a later milestone. |

## Capabilities

### v1 (must have)

- Load config from a file plus environment variables; fail fast with clear errors.
- WebDAV adapter: list, stat (ETag, last-modified, size), read, write, create folder; retries with backoff; respects mount boundaries; blocks path traversal.
- Collections: create, list (paginated, filters on indexed fields), get, replace, patch, delete. Records validated against the collection's JSON Schema. Server-generated UUID plus `createdAt` / `updatedAt`.
- `.xlsx` mirror: debounced, single-writer regeneration after changes. Columns are derived from the schema or mapped in config. Writes are atomic (upload to a temporary name, then move).
- Access policies: `anonymous` and `apiKey` (hashed keys in config or MongoDB), set per operation.
- Sheets: an `.xlsx` worksheet as JSON rows (header row gives the field names), cached and refreshed by ETag.
- Documents: `.docx` → Markdown; cached per ETag. Embedded images: v1 drops them or inlines them, chosen in config. Extracting them is v2.
- Files: list folders and download files from read mounts.
- HTTP caching: ETag / `Cache-Control` on read endpoints, so a gateway or CDN can cache them.
- OpenAPI served at `/docs`; `/health` and `/ready` endpoints.
- Structured logs (pino) with no personal data in them.
- Local dev stack: Docker Compose with MongoDB and a local WebDAV server. The integration tests run against that stack, never a real Drive.
- CI: lint, typecheck, unit and integration tests, container image build.

### v2 (later)

- OIDC/JWT validation (Keycloak) and role-based policies.
- Extracting `.docx` images into a served assets endpoint.
- GDPR erasure endpoint implementing the 5-step procedure under *Constraints and risks*, including an optional OX HTTP API client to purge the trash and old versions, and a list of erased IDs that is replayed after a backup restore.
- Webhooks or a change feed for collections.
- An S3-compatible object API. Options: run `rclone serve s3` as a sidecar (it exists but is experimental, and maps one storage credential per instance), or implement a native subset (GetObject, PutObject, ListObjectsV2, multipart).

### Out of scope

- Any organisation-specific content model (newsfeed, research index): it belongs in the consuming apps.
- Syncing edits made in mirrored `.xlsx` files back into MongoDB.
- A web UI.
- Hosting or operating Keycloak or Kong. Only reference configs are provided.

## Non-functional requirements

- **Write volume:** tens of records a week per deployment. Correctness matters more than throughput.
- **Read volume:** potentially one or more API reads per website visit. Reads must be served from cache (MongoDB or memory) without a Drive round trip on the hot path. Drive changes should show up within a configurable TTL (default 5 minutes).
- **Security:** least privilege on Drive access; secrets never in the repo; anonymous endpoints are hardened (payload size limits, schema validation, rate limits).
- **Privacy:** treat collection records as personal data. No personal data in logs. Erasure supported (v2 covers the full workflow).
- **Portability:** a single container image plus MongoDB. Must work without Kong or Keycloak.

## Proposed milestones and phases

1. **Foundation**: repo tooling, config, StorageAdapter + WebDAV adapter, MongoDB connection, health endpoints, local dev stack, CI.
2. **Collections**: CRUD, schema validation, access policies, `.xlsx` mirror worker, Kong reference config.
3. **Read-only content**: sheets → JSON, files, `.docx` → Markdown, caching and HTTP cache headers.
4. **OIDC and erasure**: Keycloak/JWT validation, role-based policies, and the GDPR erasure endpoint.
5. **Object storage**: decide between an S3 sidecar and a native subset, then build it.

## Constraints and risks

- **mailbox.org terms (checked 2026-11-21):** the General Terms and Conditions say nothing about automated access, WebDAV/Drive use, fair use or server load. The misuse clause (Business §6) forbids unlawful use and misuse of the provider's infrastructure. Webspace hosting is not part of the service; this project hosts the API elsewhere and uses Drive only as storage. The provider may terminate with two weeks' notice without giving a reason (Business §7(3)), so keep an exit path: MongoDB as the system of record plus the `StorageAdapter` interface.
- **No published WebDAV rate limits and no official support for third-party integrations.** mailbox.org has no webhooks, so changes have to be detected by polling (ETag/PROPFIND on a TTL). Write a gentle client: low concurrency, exponential backoff on 429/503, and no deep PROPFIND traversals on the hot path. Ask mailbox.org support for limits before production use.
- **Data processing agreement:** Heinlein Support GmbH offers an Art. 28 GDPR agreement covering the mailbox.org brand. The deployer must confirm it covers Drive on their plan.
- **WebDAV behaviour** of OX App Suite (locking, ETag stability, versioning, path encoding of folder names such as `Userstore/Last, First`) needs a spike in phase 1.
- **Drive versioning, trash and GDPR erasure:** overwriting the mirror adds a new file version and keeps the old ones. Files deleted over WebDAV appear to land in the Drive trash. Erasure therefore must be: (1) hard-delete the record in MongoDB; (2) delete the mirror file, never overwrite it; (3) purge it from the trash and remove its old versions; (4) regenerate a fresh mirror; (5) log the erased record ID, so the erasure is applied again if a backup is restored. Step 3 probably needs the OX HTTP API (it offers a hard-delete flag and a call that deletes all versions of a file) or a documented manual step. Plain WebDAV may not reach the trash. Spike in phase 1.
- **MongoDB licensing:** MongoDB Community is under the SSPL. Self-hosting is fine. FerretDB is an Apache-2.0 alternative to test with in CI if a fully OSI-licensed stack matters.
- **Trademark:** the project name uses "mailbox-org" only descriptively. The README states it is unofficial.
- **AI tooling policy of the first adopter:** planning artefacts and fixtures must contain only synthetic data.

## Open questions for GSD's discuss phase

1. Collection definitions: config file only (v1), or also manageable through admin endpoints?
2. API key storage: keys in a config file, or in MongoDB with endpoints to rotate them?
3. Mirror format: one workbook per collection with one worksheet, or one workbook with a worksheet per collection?
4. Should `DELETE` be a soft delete by default (keeping a tombstone) with hard delete as a separate admin operation?
5. Package manager: pnpm or npm?
6. Hosting target for the reference deployment (a single VPS with Docker Compose?).
