# OX App Suite / mailbox.org WebDAV compatibility matrix

- **Run date:** 2026-11-21 (plan 01-02)
- **Account class:** personal, fresh account
- **Method:** raw HTTP probe script plus web UI checklist
- **Anonymisation:** everything here is anonymised. Host, user folder, probe folder, dates, quota values and ETags are synthetic (`dav.example.invalid`, `Last, First`, `probe-2026-01-01`, epoch day 2026-01-01). OX ETags have been replaced by synthetic strings of the same shape; only the shape is described below.
- **Evidence:** a status line such as "PUT 201" is quoted from the reviewed `summary.json` of the run. A fixture is a recorded response body under `test/fixtures/ox/`. A claim that rests on neither is marked `[ASSUMED]`. A row that could not be tested says "not tested: REASON".
- **Dev-server comparison:** the "RFC/dev-server expectation" column describes the RFC 4918 reading and the local hacdias/webdav v5 behaviour from the research. The hacdias dry run is never used as OX evidence.

ETag shape on OX: `<number>-<number>-<number>-<number>`, sent unquoted in `getetag` and quoted in the `ETag` header. In the recording the second number is a per-file id, the third counts writes of that file (1, 2, 3, 4 across four PUTs), and the fourth is a per-write token that also changes on a rename.

## Consequences

1. **ETag as validator.** The ETag is usable on OX. It is stable across PROPFIND, HEAD, GET and sibling edits (P-06), changes on every write including identical bytes, and changes on a MOVE rename. A (lastModified, size) fallback is not safe on OX: `getlastmodified` has one-second resolution and three writes shared a second. Phase 4 should key its cache on the ETag string as the client returns it (unquoted), send it quoted and strong in If-None-Match (P-07: a weak form gets 200), and use (lastModified, size) only as a hint for servers that send no ETag. Because a rename changes the ETag, a cache keyed on path plus ETag drops stale entries on its own. An ETag change does not prove a content change.
2. **MOVE over an existing file vs plain PUT (input for the Phase 3 mirror).** Both patterns work (P-10, P-17). Temp plus MOVE Overwrite T gives a 204, leaves no temp residue (U-04) and shows no half-written file to a reader, but the destination takes a new file identity and its write counter restarts at 1 (U-03 answer lost; share-link survival `[ASSUMED]` no). A direct PUT keeps identity, adds a version (U-01, U-02) and accepts If-Match for conflict detection (P-08 gives 412 on a stale ETag). A repeated successful MOVE gives 404, which the adapter's re-check already covers. Atomicity of a half-written PUT was not probed `[ASSUMED]`. Phase 3 decides; prefer the direct PUT with If-Match unless a torn read of the workbook turns out to matter, and skip writes when nothing changed (U-02).
3. **Adapter and path-rule changes (each applied by plan 01-12).**
   - **C-0 (no change needed):** P-10, P-11, P-12 (404, 405, 409, 412 mappings), P-09 (423 to `conflict`), P-15 (path encoding), P-14 backslash (rejected as `invalid-path` before sending), P-18 (defaults stand).
   - **C-1:** P-02, P-03, P-19. OX tags `getlastmodified` with a `b:dt` attribute, so `webdav` returns `lastmod` as `{ text, "@dt" }`. `toEntry` passes it to `new Date(...)` and every OX entry gets `lastModified: null`. Expected: `lastModified` is the parsed date (read `text` when `lastmod` is an object). No error kind: it is a field mapping. **Resolved in plan 01-12:** `toEntry` reads `lastmod.text`; test `C-1: stat parses lastModified from an OX getlastmodified with a b:dt attribute`, and the replay now asserts the real value.
   - **C-2:** P-03, P-14, U-09. OX keeps NFC and NFD names as two files and lists both. `parseRelativePath` folds every segment to NFC, so a file stored in NFD form (which macOS clients create) cannot be addressed: the folded name is a different file and OX answers 404, expected kind `not-found`, and a write would create a second, NFC file. **Decided in plan 01-12: keep the fold.** NFD names stay unreachable through the adapter (they are listed as OX returns them, but a request for them goes out in NFC form); the fold also keeps mount overlap strict. Pinned by `C-2: an NFD name is addressed in its NFC form, ...` and `C-2: list keeps the NFC and NFD names ...`. Addressing names exactly as listed would weaken the normalisation rules from plans 01-03 and 01-08, so it is left to a later decision.
   - **C-3:** P-13. GET on a folder answers 415, which the adapter maps to `unavailable`. Expected kind `conflict`, as for the stat-first folder check in `read`. Low priority: the stat-first guard avoids it. **Resolved in plan 01-12:** `read` maps a 415 from the data GET to `conflict`; test `C-3: read maps OX's 415 for GET on a folder to conflict`.
4. **`Last, First` encoding and name rules.** OX answers both `Last%2C%20First` and `Last,%20First` and refuses plus forms and `%2F` (P-15). OX writes the folder href with a raw comma and file names with `%2C` (P-03); the client decodes both, shown by the replay test. NFC and NFD names are distinct (P-03, P-14). Case sensitivity is inferred only (`[ASSUMED]`, P-14). Trailing dots and spaces, `: ? * " < >`, pipe and 260-character names were accepted; only the backslash failed (500).
5. **Versions and trash (feeds the v2 GDPR erasure work).** Every overwrite keeps a version, identical writes included (U-01, U-02). DELETE moves a file or a whole folder to the trash as one entry (U-05, U-06) and the trash can be emptied in the UI (U-08). So a WebDAV DELETE does not erase data: versions and trash copies remain until someone purges them, and no WebDAV purge call was probed. Erasure for GDPR in v2 must cover versions and the trash. Whether versions travel with a trashed file is unproven (U-05).
6. **Open items for production.**
   - Ask mailbox.org support about WebDAV request limits (D-09): the `x-ratelimit-limit` header shows 150 per second, 3000 per minute and 20000 per hour, but nothing says whether that is per account or per app password, and no 429 or Retry-After was ever seen.
   - The run used a personal, fresh account: business accounts and larger folders were not tried.
   - Quota is not readable over WebDAV (P-16) and 507 behaviour is untested.
   - Case sensitivity (P-14), COPY (P-01), trash purge over WebDAV (U-08), whether trashed files keep versions (U-05) and the UI display of NFC versus NFD names (U-09) are untested.
   - Uploads above 10 MB were not tried.
   - The P-07 order in the 01-02 SUMMARY differs from the recording; this document follows the recording.
